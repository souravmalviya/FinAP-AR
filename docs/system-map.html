The one principle behind all of it: AI runs only at the edge where data is messy (reading the PDF). The moment data is clean, deterministic rules take over — because money must be exact and auditable. AI never decides what to pay. And the ERP is the memory: every step either reads from it or writes to it.

The trusted core. Stores financial truth, enforces the invoice lifecycle, knows nothing about AI. Backend + a single-file frontend in one deployable unit.

The automation pipeline. Its database stores workflow (documents, extractions, approvals, audit) — never financial truth. It reaches the ERP only through one adapter file.

The document status journey (IngestedDocument.status)

RECEIVED → QUEUED → EXTRACTING ──→ MATCHED ──→ PENDING_APPROVAL → APPROVED → PAID
                        │                │            │
                        │                └─(<50k)──→ APPROVED (auto — skips human)
                        │                             │
                        ├─→ NEEDS_REVIEW  (rule failed: mismatch / unknown vendor / no PO)
                        ├─→ DUPLICATE     (same file hash OR same invoice no in ERP)
                        └─→ FAILED        (crash after 3 queue retries)          REJECTED (human said no)

7. Three traces to follow in the code

Print this section and follow each trace with the files open. This is the fastest way to truly own the codebase.

Trace A — happy path (₹2,50,000 invoice, matches PO)

1
Upload hits app.ts → bytes stored via storage.ts, sha256 via hash.ts, row created (QUEUED), audit "INGEST" server/src/app.ts
2
enqueueDocument() writes the job into Valkey; HTTP returns 201 immediately pipeline/queue.ts
3
Worker fires processDocument() → idempotency guard (status must be QUEUED) pipeline/processDocument.ts
4
EXTRACT: pdfText.ts pulls text → engine from extraction/index.ts returns JSON → saved as Extraction row, audit "EXTRACT (AI)"
5
VERIFY: verify.ts — fields ✓, vendor found via erpClient.listVendors ✓, PO found ✓, same vendor ✓, amounts equal ✓ → audit "VERIFY (RULE)"
6
erpClient.createInvoice() → ERP's invoice.service.ts validates again (duplicate? vendor belongs to org? PO same vendor?) → creates invoice → auto-marks PO MATCHED
7
ROUTE: route.ts → 2.5L is in 50k–5L band → ApprovalTask(FINANCE_HEAD) created → ERP invoice → PENDING_APPROVAL → audit "ROUTE (RULE)"
8
Human clicks ✓ in approvals/page.tsx → app.ts decideApproval() → ERP first, then local records → audit "APPROVAL (HUMAN)"
9
"Record Payment" → app.ts /pay → erpClient.createPayment() → ERP's atomic transaction: payment + invoice PAID + PO CLOSED → audit "PAY"

Trace B — the exception (invoice ₹2,90,000 but PO says ₹3,00,000)

1
Steps 1–4 identical (ingest, queue, extract)
2
verify.ts rule 5: Number(po.amount) !== extracted.amount → returns { ok:false, reason:"Amount mismatch…" }
3
processDocument.ts sets status NEEDS_REVIEW + failReason, audits "VERIFY (RULE) FLAGGED", and returns — the pipeline stops. Nothing was written to the ERP. No money can move.
4
Dashboard shows the red badge + 🚩 reason on the detail page. (Resolving it from the UI = a future feature.)

Trace C — the automation payoff (₹30,000 invoice, clean)

1
Steps 1–6 identical — extract, verify, ERP write, PO matched
2
route.ts: 30,000 < 50,000 → { kind:"AUTO_APPROVE" }
3
ERP invoice set APPROVED directly; no ApprovalTask is ever created — the invoice never appears in any human's inbox. That's the product's whole value in one trace.

8. The two databases — and why they're separate

mini_erp (the ERP's)finerp_ap (the product's)
Storesfinancial TRUTH: Vendor, Customer, PurchaseOrder, Invoice, PaymentWORKFLOW: IngestedDocument, Extraction, ApprovalTask, WorkflowEvent (audit)
OwnerminiERP onlypipeline only
Why separateIn reality the customer's ERP already exists (QuickBooks/SAP) — you'd never share its database. The product must treat the ERP as a foreign system reachable only by API. Merging them would build something that can't exist in production.
Shared ruleevery table in BOTH has organizationId — multi-tenant from day one

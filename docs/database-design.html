1. Why two databases

Verity's own database (finerp_ap) stores the workflow: documents, what the AI read, approval tasks, the audit trail, users and organizations. The ERP database (mini_erp) stores financial truth: vendors, purchase orders, invoices, payments. They never share tables - Verity reaches the ERP only over its REST API, exactly as it would reach a customer's ERPNext or QuickBooks. If the two ever disagree about money, the ERP wins.

3. mini_erp - the ERP database (ER diagram)

Every table carries organizationId (the tenant tag the ERP receives as x-org-id). Money is always DECIMAL(14,2).

4. How the two databases connect (no shared tables!)

The bridge in one sentence: Verity's Organization row translates "my org" into "that ERP, that URL, that company tag"; the ERP filters everything by the tag it receives; and Verity remembers the ERP's record ids (erpInvoiceId, erpPoId) as plain strings, because you cannot have real foreign keys across two databases - referential integrity across systems is maintained by the API + the conflict-reconciliation logic, not by PostgreSQL.

7. The design principles this schema encodes

PrincipleWhere you see it
Money is DECIMAL, never floatevery amount column is DECIMAL(14,2) - floats cannot represent 0.10 exactly
Duplicates die at the databaseUNIQUE(org, sha256) for files; UNIQUE(org, type, invoiceNo) for invoices - even buggy code cannot insert twice
The workflow is a state machinestatus enums + ALLOWED_TRANSITIONS; illegal jumps get a 400, not a corrupted state
Multi-tenancy on every roworganizationId everywhere; in Verity the tenant comes from the login token, never from client input
Audit is append-onlyWorkflowEvent rows are never updated or deleted; corrections are new events
Cross-system links are API refs, not FKserpInvoiceId/erpPoId are strings; consistency across systems is the pipeline's job (ERP wins on conflict)
Delete is restricted where money livesPayment→Invoice is ON DELETE RESTRICT; Organization→User RESTRICT
